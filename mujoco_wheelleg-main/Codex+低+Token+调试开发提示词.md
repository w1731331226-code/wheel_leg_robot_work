工作原则：

1. 最小上下文
- 只读取完成当前任务必须的文件。
- 优先通过文件名、符号、函数名、报错信息定位目标。
- 不要主动扫描整个项目。
- 已读取且没有变化的文件不要重复读取。
- 不要为了“了解架构”额外阅读无关模块。

2. 最小分析
- 不需要给我长篇推理、背景介绍或教学说明。
- 内部完成必要分析即可。
- 输出只保留：
  ① 问题定位
  ② 修改内容
  ③ 验证结果
  ④ 尚存问题
- 每项尽量控制在几句话内。

3. 调试优先
当前阶段目标是“让功能正确工作”，不是优化整个项目。

遇到问题时按以下顺序：
报错/异常现象
→ 定位直接原因
→ 找到最相关代码
→ 做最小修改
→ 编译/测试
→ 根据结果继续修正。

不要一开始进行大规模架构分析。

4. 最小修改
- 优先修改最少数量的文件和代码行。
- 不做与当前任务无关的重构。
- 不主动改变量名、目录结构、接口设计或代码风格。
- 不因为“代码可以更优雅”而修改正常代码。
- 除非当前问题确实由架构导致，否则不要重构。

5. 限制探索深度
如果有多个可能原因：
- 先验证概率最高的 1～2 个。
- 不要一次性展开所有可能性。
- 一个假设验证失败后，再进入下一个。
- 不要提前研究尚未出现的问题。

6. 使用已有信息
优先相信：
- 衔接文档
- 当前开发计划
- 已知硬件配置
- 已确认接口
- 上一次调试结论

除非当前现象与它们冲突，否则不要重新验证已经确认的内容。

7. 文件读取约束
开始工作前：
- 先从衔接文档确定本次任务涉及的模块。
- 然后只打开最可能相关的 1～3 个代码文件。
- 确有必要时再扩大范围。

如果通过搜索符号或关键词可以定位代码，不要逐文件阅读。

8. 硬件/机器人项目约束
涉及轮腿机器人时，优先关注实际执行链路：

传感器输入
→ 状态估计
→ 控制算法
→ 指令生成
→ 通信
→ 电机驱动
→ 实际反馈。

只分析与当前故障所在链路附近的模块，不主动分析完整控制系统。

涉及 CAN、UART、SPI、编码器、电机、电流环、速度环、位置环、姿态控制等问题时，先检查最直接的数据流和接口，不先讨论理论优化。

9. 修改前检查
修改代码前，只需要确认：
- 当前现象是什么
- 最可能原因是什么
- 准备修改哪里
- 修改是否可能影响其他已正常功能

确认后直接修改，不需要输出详细计划。

10. 修改后验证
优先执行最小验证：
- 编译
- 相关单元测试
- 相关脚本
- 针对当前模块的运行测试

不要为了一个局部修改运行全部测试，除非确有必要。

11. 停止条件
满足以下条件后停止继续探索：
- 当前问题已修复；
- 编译/目标测试通过；
- 本次计划中的目标已完成。

不要在任务完成后继续主动寻找其他潜在问题。
