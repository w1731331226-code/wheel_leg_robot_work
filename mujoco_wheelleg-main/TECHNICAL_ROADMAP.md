## 1. 总体结论

项目按以下依赖顺序推进：

```text
可信物理模型
    ↓
抗扰 LQR + VMC
    ↓
同一控制核完成实机闭环
    ↓
ROS 2 平面自主导航
    ↓
三维地形感知与机动决策
    ↓
残差 PPO 增强
```

LQR + VMC 长期保留为安全控制底座。PPO 首版只输出有界残差或动作参数，不直接接管六路电机裸力矩。ROS 2、雷达和 Nav2 不进入底层实时平衡环。

## 3. 目标系统架构

```text
3D 雷达/深度相机 ─→ 定位 + 局部高程图 ─→ Nav2 + 地形机动管理器
                                                │
                                   vx / wz / 腿高 / 动作请求
                                                ↓
                              安全监督、限速、命令仲裁（ROS 2）
                                                ↓ 50～200 Hz
IMU/编码器/电流 ─→ 实时状态估计 ─→ LQR + VMC + 状态机 ─→ 六路电机
                       500～1000 Hz                ↑
                                      PPO 有界残差，后期约 50 Hz
```

建议频率只是起始值，最终以实机延迟和计算余量标定：

- 电机电流环：驱动器内部，通常 10～20 kHz；
- 姿态估计、LQR、VMC、接触状态机：500～1000 Hz；
- 上层速度、腿高和动作命令：50～200 Hz；
- PPO 推理：约 50 Hz；
- 地形感知和局部规划：10～30 Hz。

### 阶段 2：增强 LQR + VMC 抗扰和地形能力（2～5 周）

控制结构：

- 六状态增益调度 LQR：首版按腿长插值；速度/接触按独立场景验证，证据表明确需新增调度维度后再扩展；平台 roll/pitch 参考恒为 0；
- VMC 阻抗：左右腿独立支撑力、腿长和阻尼，承担 roll、落地和不平地适应；
- 姿态/速度状态估计：底层本地运行，不依赖 ROS 2 网络；
- 接触估计：由电机电流、关节运动、IMU 和可选力传感器融合；
- 统一饱和优先级：先保姿态和安全，再保位置、速度和动作性能；
- 防积分饱和、命令斜坡、关节软限位、轮胎滑移检测和峰值扭矩计时；
- 坡地模式：估计地面法向，生成合理的车身、腿长和速度参考；
- 越障模式：滚行、降低速度、调腿、绕行、跳跃采用明确状态机。

外力碰撞恢复采用：

```text
NORMAL → PUSH_RECOVERY → RECAPTURE → HOLD
```

- `PUSH_RECOVERY`：检测到大角速度、速度突变或力矩饱和后，暂时释放原停车位置目标，优先恢复姿态和速度；
- `RECAPTURE`：在可停止区域重新捕获平衡点；
- `HOLD`：以新的稳定位置为参考，不强行回到碰撞前位置；
- 第一版不增加扰动观测器；只有状态反馈无法达到验收指标时再加入。

出口门：通过第 5 节的复杂地形与物理碰撞矩阵。若主要失败来自硬约束和饱和，再只对必要部分引入 QP/MPC，不整体替换 LQR + VMC。

### 阶段 3：统一控制核、HIL 和实机闭环（3～6 周）

任务：

- [ ] 只保留一套正式控制逻辑；建议整理为无 ROS、无 MuJoCo 依赖的确定性 C++ 控制核；
- [ ] Python 仅保留为仿真、测试和数据分析入口；
- [ ] MuJoCo 适配器、MCU/实时控制器和后续 ROS 2 控制器复用同一输入输出定义；
- [ ] 实时循环禁止动态内存分配、文件 I/O 和阻塞日志；
- [ ] 完成 CAN FD/EtherCAT/串口硬件接口及时间戳；
- [ ] 完成硬件在环、吊架、低腿高、低速度、全速度逐级验证；
- [ ] 加入物理急停、软件看门狗、命令超时、倾倒、过流、过温、欠压和传感器失效保护；
- [ ] 记录 rosbag/二进制实时日志，用于仿真参数回标。

出口门：

- 实机连续运行不出现周期超时和通信失控；
- 上位机断联后进入确定的安全状态；
- 实机与 MuJoCo 在相同输入下的关键响应趋势一致；
- 平地碰撞恢复达到约定等级后，再接入自主导航。

### 阶段 4：ROS 2 平面自主导航（2～4 周）

推荐稳定基线：Ubuntu 24.04 + ROS 2 Jazzy。当前开发机为 Ubuntu 22.04，不建议新项目继续以 Humble 为长期基线。Lyrical 支持周期更长，但只有在电机、雷达、Nav2 和 MuJoCo 相关依赖全部验证后再迁移。

任务：

- [ ] 建立 URDF/Xacro、`base_link`、`base_footprint`、`odom`、`map` 和传感器 TF；
- [ ] 建立 `ros2_control` 硬件接口和生命周期；
- [ ] 发布 `joint_states`、IMU、里程计、诊断和控制状态；
- [ ] 使用 `robot_localization` 融合轮速里程计与 IMU，服务导航；
- [ ] 使用 `slam_toolbox` 完成二维建图/定位；
- [ ] 接入 Nav2、速度平滑和 Collision Monitor；
- [ ] 建立命令优先级：急停 > 安全恢复 > 遥控 > 地形动作 > Nav2；
- [ ] 使用官方 `mujoco_ros2_control` 接入仿真，避免维护自定义 MuJoCo-ROS 桥；
- [ ] 验证 ROS 2 节点重启、雷达超时、定位跳变和命令超时不会破坏底层平衡。

出口门：在平坦或缓坡环境中完成建图、重定位、连续目标导航、动态减速和紧急停车，底层平衡不依赖 ROS 2 消息实时性。

### 阶段 5：复杂地形感知与自主机动（4～8 周）

传感器原则：

- 水平 2D 雷达可以承担平面建图定位，但不能可靠测量坡度、地面粗糙度、下台阶和台阶高度；
- 复杂地形至少使用 3D 激光雷达，或使用 2D 雷达定位并增加前下视深度相机；
- 所有传感器必须硬件或软件时间同步，并测量端到端延迟。

局部地图至少包含：

- 高度及置信度；
- 坡度和地面法向；
- 粗糙度；
- 正/负台阶高度；
- 可通行代价；
- 感知盲区和过期区域。

规划分层：

1. Nav2 负责全局路径和普通二维避障；
2. 局部高程图负责判断地形是否可滚行、可调腿、可跳或不可通行；
3. 地形机动管理器输出限速、左右腿高、跳跃准备和动作模式；
4. 底层状态机负责动作安全门，不接受不满足姿态、速度、接触或距离条件的跳跃请求。

当前 15 cm 台阶有效触发距离为 0.84～0.96 m；在 1 m/s 下窗口约 120 ms。第一版目标应将端到端时间误差控制在约 30 ms、距离误差控制在约 3 cm，并保留减速或取消动作的余量。该指标来自当前回归窗口推导，必须通过实机重新标定。

出口门：在未预先写死台阶坐标的情况下，机器人能够识别地形、选择动作、完成或安全取消，并通过组合地形回归。

### 阶段 6：PPO 运动增强与 sim-to-real（6～12 周）

前置条件：阶段 1～5 的模型、实机日志、安全控制和地形输入已经稳定。否则 PPO 会学习利用仿真漏洞。

首版策略：

- PPO 不输出裸六路电机力矩；
- 输出左右腿长/支撑力小残差、轮力矩小残差，或跳跃时机、下蹲深度、落地阻尼等动作参数；
- 残差初始限制在实机允许力矩的 10%～20%；
- 策略超时、NaN、姿态越界、通信异常或安全状态触发时，残差立即归零；
- 经典控制器始终可以独立维持安全。

建议观测：

- 重力方向和机身角速度；
- 主动关节位置、速度和电流；
- 轮速与估计底盘速度；
- 接触概率；
- 用户速度/转向命令；
- 前几步动作；
- 局部地形高度采样或压缩特征。

课程顺序：

1. 平地速度跟踪；
2. 随机物理推撞；
3. 摩擦与坡度变化；
4. 不平地；
5. 台阶与落地；
6. 质量、惯量、电压、延迟、噪声、间隙和电机差异随机化；
7. 所有条件组合和未见参数测试。

域随机化范围必须来自实测或合理误差边界，不使用任意的大范围随机数。训练优先沿用 MuJoCo MJX/MuJoCo Playground，避免同时迁移到第二套仿真器。

部署顺序：离线回放 → 仿真对照 → 实机影子模式 → 10% 残差 → 逐级扩大。只有保留集和实机指标均优于 LQR + VMC 基线时，才允许扩大 PPO 权限。

PPO 解决的是运动策略增强，不等于完整具身智能。语义理解、任务规划和多模态交互以后放在 Nav2/地形管理器之上，并保持不能绕过安全控制层。

## 5. 验收体系

### 5.1 外力碰撞测试

使用 MuJoCo `xfrc_applied` 对车身施加真实有限时长的力和力矩；每次脉冲后清零，不直接修改 `qvel`。

当前模型总质量约 1.018 kg，仿真初始冲量等级可从 0.2 N·s、0.5 N·s 逐级增加，最终范围由实机安全实验冻结。

覆盖维度：

- 方向：前、后、左、右、偏航；
- 作用点：质心附近、车身顶部；
- 时长：50、100、150 ms；
- 状态：静止、0.5 m/s、1 m/s、转向、急停、跳跃落地；
- 地形：平地、纵坡、横坡、不平地、台阶台面；
- 参数：不同质量、摩擦、延迟、电压和传感器噪声。

建议验收目标：

- 正常无碰撞运动：roll/pitch 峰值不超过约 5°；
- 碰撞恢复瞬态：不倒地，roll/pitch 峰值不超过约 15°；
- 2 s 内恢复到 3°以内及低速稳定区；
- 无持续非轮部件触地；
- 无关节硬限位、非法输出和超出允许时间的峰值电流；
- 记录恢复位移，但不要求强行回到碰撞前原点；
- 每个等级至少 100 个可复现随机种子。

这些数值是第一版工程目标，必须依据实机安全边界调整。

### 5.2 地形矩阵

| 场景 | 变量 | 核心指标 |
|---|---|---|
| 平地 | 速度、转向、急停 | 姿态、速度误差、停车距离、抖动 |
| 纵坡 | 角度、摩擦、上下坡 | 姿态、滑移、力矩余量 |
| 横坡 | 角度、左右高度差 | roll、左右腿行程、轮胎侧滑 |
| 不平地 | 高度、波长、随机种子 | 通过率、接触稳定、车身加速度 |
| 正台阶 | 高度、距离误差、速度 | 识别率、动作选择、起跳窗口、落地稳定 |
| 外力碰撞 | 冲量、方向、作用点 | 峰值姿态、恢复时间、位移、饱和 |
| 组合场景 | 地形 + 碰撞 + 噪声 | 失败率、安全降级、可重复性 |

### 5.3 实机安全门

- 急停必须独立于 ROS 2 和 PPO；
- 命令、IMU、编码器或通信超时均进入已定义安全状态；
- 所有力矩、速度、位置、电流、温度和电压有硬限制；
- PPO、导航或感知失效时，经典控制器仍可稳定或安全停机；
- 任何软件算法都不能假设存在当前结构无法产生的基座力或空中 roll/yaw 力矩。

## 6. 关键工程决策

2026-09-05 已根据用户要求完成 RoboMaster 开源方法核对，选型与代码证据见 [控制方法参考与选型](CONTROL_METHOD_REVIEW_2026-09-05.md)。本轮增加方案记录、复现两项已有失败，并根据用户允许加宽的要求完成 16 场景轮距敏感性检查，选择 180 mm 轮距作为结构候选；正式 XML 仍为 108 mm，未修改控制器或改变阶段判定。下一步采用本机模型求解的腿长调度 LQR、VMC 和接触事件驱动跳跃；局部 QP/MPC 以约束冲突的验证结果决定是否引入。

### 6.1 保留 LQR + VMC，不立即上全量 MPC

先使用增益调度、接触感知、饱和优先级和恢复状态机扩展当前控制。只有确认主要失败来自多变量硬约束，而不是模型、传感器或执行器不足时，再为局部功能增加 QP/MPC。

### 6.2 不维护两套正式控制逻辑

正式控制核只保留一套 C++ 实现；Python 负责仿真编排、回归和训练。这样可以避免 Python 与 `wheelleg.cc` 参数和状态机继续分叉。

### 6.3 不再增加第二套仿真器

继续使用 MuJoCo。ROS 2 阶段使用官方 `mujoco_ros2_control`；PPO 阶段优先使用 MJX/MuJoCo Playground。只有 MuJoCo 无法表达明确需求时才评估其他仿真器。

### 6.4 二维导航和地形机动分层

Nav2 保持负责全局路线和普通避障；复杂地形使用局部高程图和一个小型机动管理器。不要修改 Nav2 核心，也不要让 Nav2 直接控制跳跃阶段。

### 6.5 机械能力不足时不靠算法掩盖

当前结构在腾空时没有真实的 roll/yaw 执行通道，不能承诺强侧向空中碰撞恢复。若地面侧撞也频繁饱和，优先评估降低质心、加宽轮距、轮胎和执行器能力，而不是继续提高控制增益或 PPO 权限。

## 8. 风险登记

| 风险 | 影响 | 当前对策 |
|---|---|---|
| 仿真使用不存在的基座力矩 | 策略无法实机复现 | 阶段 1 强制六执行器边界 |
| 峰值电机能力不明确 | 跳跃与碰撞恢复可能不可实现 | 阶段 0 冻结扭矩-转速和热限制 |
| 球形轮胎接触失真 | 横坡、不平地、台阶结果失真 | 轮胎接触和摩擦实测校准 |
| 真值速度/接触泄漏 | 实机状态机无法工作 | 统一 Observation 和状态估计 |
| 2D 雷达无法识别地面 | 台阶、坡度和负障碍误判 | 增加 3D 雷达或前下视深度 |
| 台阶触发窗口过窄 | 延迟导致起跳失败 | 时间同步、距离置信度、减速和取消机制 |
| Python/C++ 控制分叉 | 仿真通过而实机代码不同 | 唯一 C++ 控制核 |
| ROS 2 抖动进入平衡环 | 丢包或调度导致跌倒 | 实时控制与 ROS 2 分层、看门狗 |
| PPO 利用仿真漏洞 | sim-to-real 失败 | 无辅助力基线、实测域随机化、残差策略 |
| 机械结构缺少空中侧向控制 | 强侧撞无法靠软件恢复 | 明确能力边界，必要时机械改型 |
