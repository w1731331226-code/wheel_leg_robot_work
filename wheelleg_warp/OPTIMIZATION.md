# GPU闭环与动画优化记录（2026-09-21）

## 为什么吞吐高、画面仍慢

原704k物理步/秒的数字来自256世界开环CUDA图回放，不含Python控制、奖励、PPO、逐步回读。正式训练则是8个单世界进程，每个策略步有40个物理子步，CPU控制器每0.5ms都要拿到新状态。界面“策略步/秒”还是8环境总和：例如合计80策略步/秒，环境0只有约10个新画面/秒，不能等同80 FPS。

此外，旧保存GIF只取每两个50Hz状态中的一个，即25 FPS；实时HTTP轮询上限约5 FPS，渲染循环约10 FPS，且同一循环同步导出整段GIF时会暂停两侧直播。这些是实现瓶颈，现已调整。

[MuJoCo官方文档](https://mujoco.readthedocs.io/en/latest/mjwarp/)明确区分批量吞吐和单环境低延迟；[Warp 1.17 FAQ](https://nvidia.github.io/warp/v1.17/user_guide/faq.html)说明CUDA数组的numpy读取会复制到主机，推荐使用范围更窄的同步。

## 已实施

- 新 `PackedPhysics` 保留原GPU物理求解、步长和控制顺序；审计所有消费字段后，只回读qpos/qvel、传感器、ctrl、实际执行器力、subtree_com、接触几何与摩擦、时间和溢出标志。
- GPU端把这些字段打包；固定页主机内存复用，控制上传、物理步、打包、回传共用CUDA图。每步只等待当前流一次，避免完整 `get_data_into` 中大量小传输、主机分配和无用矩阵回填。
- 该精简主机MjData只用于已审计的训练环境和控制器，未回填字段不可当作完整MuJoCo状态使用；旧完整回读类与原CPU均保留。
- 直播读取/发送上限提高到约60次/秒，但只显示实际收到的训练状态，不伪造新帧。原始采样供应更慢时，真实直播也会慢。
- 录像导出改为独立后台子进程，不阻塞直播。使用全部50Hz原始状态生成20ms/帧的50 FPS GIF及更紧凑WebP，保留旧25 FPS文件。前端有“50 FPS录像 / 返回实时”切换，回放明确标注非当前采样。WebP样例约为同帧率GIF的28%，更适合页面播放。

## 实测与边界

| 检查 | 结果 |
|---|---|
| 同GPU状态完整/打包回读 | 所有控制/奖励消费字段逐值一致 |
| 非对称越障6秒、12000物理步 | 接触数0/2/3变化及实际bump_L接触均覆盖，逐值回读核对通过 |
| 单环境800物理步，3次中位数 | 旧5.271秒 → 新1.242秒，观测4.24倍 |
| 4000策略步PPO采样/更新 | 旧GPU167.882秒 → 新GPU58.331秒，观测2.88倍 |
| 同预算CPU采样/更新 | 34.890秒；GPU仍约慢1.67倍，不宣称已超过CPU |
| 续训探针 | GPU20000→22000、CPU60000→62000各2000步通过，不使用探针模型进入正式训练 |
| CPU4000步策略权重 | 与优化前逐值一致 |
| GPU4000步策略权重 | 非逐位一致，最大参数差0.01030；首回合首次状态差异出现在接触附近第159个策略帧，qpos数值差5.12e-9。不能把字段回读相同扩大为跨运行整条训练轨迹逐位相同 |

短测时本机仍有历史CPU实验和渲染任务，不能将单次PPO倍率外推成全预算固定提速。完整评估周期仍使用同一CPU32场景；它的耗时、CPU控制器和未真正批量化的8个GPU单世界进程仍限制端到端表现。未改变奖励、动作维数、环境数、更新预算或研究门去制造提速。

证据位于 `results/packed_transfer_20260921/` 以及 `results/formal_cpu_warp_fast_v1_20260921/` 的smoke与resume_probe目录。

## 正式切换

当前正式目录为 `results/formal_cpu_warp_fast_v1_20260921/`，入口 `train_optimized.py`，服务仍为 `wheelleg-cpu-warp-formal.service`。CPU从原60000检查点、GPU从原20000检查点恢复策略、Adam优化器和VecNormalize，当前段到达总200万步即结束，后续种子仍从随机初始化开始。保存所有旧目录，不从零丢掉已有学习成果。

环境和随机流重新初始化，属于不同恢复步数的分段运行，不是精确轨迹续训；最终比较必须披露此限制。报告当前段耗时时不能称为无中断全程耗时，旧段成本仍在来源目录。原GPU/CPU接触差异也未被本次传输优化消除。前端ETA对继承步数作扣除，避免把恢复的旧进度算成新速度。
